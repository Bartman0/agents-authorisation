Sequence · Agent authorisation demo

The agent holds a handle, the database holds the intent

Two properties are visible in the shape of the flow. The user token crosses from Keycloak to the broker and stops there; what reaches the agent is a session handle and, later, a 120-second delegated token. And the approval traffic runs between the user and the broker past the agent's lifeline, never through it: if approval arrived on the agent's own channel, the agent would be approving its own requests.

The last two messages are the point of the lower half. The write token authorises "payments", not this payment; the INSERT is accepted only because postgres/init/04-approvals.sql finds an unconsumed approval matching the account, amount, counterparty and description the user read at message 9. Files: broker/broker.py (handle, scopes, approval), broker/authz.py (the policy decision), agent/identity.py (the agent's whole credential surface), postgres/init/02-rls.sql (the row-level backstop). The read path through query_transactions is the same shape without messages 7 to 13 and 15 to 16: a finance:read token, a SELECT-only role and a READ ONLY transaction.
